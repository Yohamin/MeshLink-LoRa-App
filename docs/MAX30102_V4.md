# MAX30102 opcional — Heltec V4.3 / V4.3.1

Introducida en firmware 5.3.0 / app 1.1.5; fuente actual: firmware **5.6.0**,
app **1.4.0 / código 10**, con [mediciones locales y envío manual](MEDICIONES_MAX30102.md).
La fuente V4.3.1 conserva la corrección FIFO r2 y añade metadatos BLE de diagnóstico r3;
se identifica al arrancar como `[HEALTH-DIAG r3]`, no sustituye los binarios
ya empaquetados. Ver [cómo compilarlo y capturar el diagnóstico](MAX30102_DIAGNOSTICO.md).
Solo el perfil `V4_3` (43) habilita esta capacidad; V3, V4.2 y V4-R8
no la activan. Se conservan GPS, mensajería y protocolo LoRa 5.1.

**La adquisición no está validada con el sensor físico. No es un dispositivo médico:**
las estimaciones de pulso y SpO₂ son experimentales, sin calibración ni
validación clínica. No usarlas para diagnóstico, tratamiento ni decisiones
en emergencias sanitarias. No hay alarmas médicas.

## Conexión: primero confirmar la alimentación

La foto muestra la fila inferior `VIN SDA SCL GND`, pero no confirma el
fabricante, regulador, rango de VIN ni tensión de las resistencias pull-up.
Solicitar ficha técnica o enlace del módulo antes de energizarlo. No asumir
que admite 5 V ni que la alimentación interna del chip equivale a VIN.
Los GPIO del ESP32 deben recibir señales compatibles con lógica de 3,3 V.

| Pin del módulo fotografiado | Heltec V4.3.1 / perfil 43 |
| --- | --- |
| SDA | GPIO4 |
| SCL | GPIO6 |
| GND | GND común |
| VIN | Pendiente de confirmar en la ficha del breakout; usar 3,3 V únicamente si está expresamente admitido |
| INT, RD, IRD | Sin conectar para esta implementación |

No modificar los puentes `1V8` / `3V3` sin el esquema del módulo. Realizar
conexiones con la alimentación desconectada. Confirmar la serigrafía y
continuidad de los cables: la orientación de una fotografía puede confundir.
GPIO4/6 se usan en un bus I²C separado del OLED; no reutilizar pines de GPS,
FEM o radio. Mantener cables cortos y comprobar pull-ups a tensión adecuada.

## Firmware y Arduino IDE

Entregar la carpeta `firmware` completa, con `firmware.ino` y los cinco
encabezados: `board_profile.h`, `nmea_gps.h`, `routing_policy.h`,
`health_signal.h`, `max30102_sensor.h`. Las pestañas adicionales son normales.

Bibliotecas: RadioLib 7.8.1, ArduinoJson 7.4.3, U8g2 2.36.19 y **SparkFun
MAX3010x Pulse and Proximity Sensor Library 1.1.2**. Esta última está instalada
en este equipo. Su encabezado se llama `MAX30105.h`, aunque admite MAX30102;
el ID 0x15 no distingue esos dos modelos. El código no identifica el modelo
únicamente mediante ese ID. Usa el algoritmo de referencia de la biblioteca.

En una copia para Arduino IDE, antes de los `#include` de `firmware.ino`:

```cpp
#define MESH_BOARD_PROFILE 43
```

Seleccionar Heltec WiFi LoRa 32 (V4), no R8; core Heltec 3.3.8, flash 16 MB,
QSPI PSRAM, USB CDC On Boot habilitado, FEM `USE_KCT8103L_PA` y ganancia de
recepción del FEM habilitada. Ver también [V4_GPS.md](V4_GPS.md).
Con el script se selecciona el perfil mediante `-Board`; no añadir además
un `#define` fijo que contradiga otros perfiles.

Desde PowerShell normal, situado en la raíz del repositorio:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\firmware\build-firmware.ps1 -Board V4_3 -ConfigFile 'C:\Users\Yohamin\.arduinoIDE\arduino-cli.yaml'
```

Compilar no carga la placa si no se especifica `-Port`. Confirmar versión
5.6.0 en el monitor después de cargar. No usar los binarios anteriores 5.2
para comprobar esta función. La app nueva se genera por separado mediante
`build-android-release.ps1`; el APK 1.1.4 existente tampoco la contiene.

## Uso y comportamiento

1. Verificar cableado y alimentación; cargar firmware y app nuevos.
2. Conectar por BLE. En Ajustes aparece la sección MAX30102 experimental.
3. Activar el interruptor. La confirmación del comando no prueba que el
   sensor esté presente: comprobar su estado posterior.
4. Apoyar el dedo suavemente, inmóvil y protegido de luz ambiente intensa.
   Se requieren 100 muestras continuas (unos 4 segundos) antes del cálculo;
   se vuelve a calcular cada 25 muestras, aproximadamente un segundo.
5. Al retirar el dedo, interrumpirse muestras, saturarse la señal o perder
   validez, los valores se ocultan. La app también oculta valores antiguos.
   Puede ser necesario esperar otra ventana completa.
6. Desactivar al terminar. Cada reinicio deja el sensor desactivado.

El worker dedicado adquiere rojo/IR a 25 muestras FIFO/s (100 Hz con promedio
de cuatro), sin esperar un dedo dentro del bucle de la red. Comprueba errores
I²C, pérdida de configuración y desbordamientos FIFO; invalida la ventana
ante discontinuidades. Los umbrales de señal y los límites numéricos no son
criterios médicos ni garantizan exactitud ante movimiento u otros artefactos.
La pantalla OLED alterna estimaciones marcadas `EXP` con el estado habitual.

Monitor serie: `health on`, `health off`, `health`. Este último muestra estado,
contadores y diagnóstico r3, no los valores personales. `health diag on`
habilita ese diagnóstico cada dos segundos, `health diag off` lo detiene;
no activan la adquisición. El teléfono recibe estimaciones,
muestras crudas y contadores por BLE aproximadamente cada segundo.

## Privacidad y límites

No hay envío automático de salud por LoRa, nube ni alarmas médicas.
La app 1.4 permite guardar sesiones locales con consentimiento y compartir
una instantánea cifrada tras confirmar destino; no envía todo el historial.
Ver [almacenamiento, privacidad y límites](MEDICIONES_MAX30102.md).
La clave AES de mensajes LoRa **no protege este canal BLE**: esta función
no añade autenticación de usuario ni emparejamiento seguro. Otro teléfono
cercano capaz de conectarse puede consultar datos o activar el sensor.
El interruptor no constituye una barrera de seguridad.

Desactivar solicita apagado lógico al sensor; no corta VIN físicamente.
Ante fallas de bus, no se puede garantizar ese apagado: desconectar la
alimentación para asegurar que no mida. El SOS de ubicación no añade salud;
un informe manual con «Necesito ayuda» sí usa el indicador SOS existente.

## Verificaciones pendientes con hardware

- Sin sensor: debe indicar no detectado y mantener LoRa/GPS/BLE operativos.
- Activar, retirar/recolocar el dedo y reiniciar: ocultar valores inválidos,
  repetir calentamiento y arrancar desactivado.
- Desconectar BLE: no conservar lecturas visibles como si fueran actuales.
- Comprobar errores I²C/FIFO y recuperación tras interrupciones; no hacer
  cambios de cableado con el equipo alimentado.
- Enviar mensajes/ACK y usar GPS mientras se mide; vigilar reinicios,
  alimentación, pérdida de muestras y contadores, especialmente durante TX.
- Comparar contra una referencia validada y documentar límites antes de
  cualquier investigación; una comparación informal no valida uso clínico.

## Validación realizada en este entorno

- TypeScript: `npm run typecheck`, correcto.
- Node: pruebas de GPS/BLE, salud, sesiones, envío y ensayos (incluidas las nuevas de registro MAX30102).
- C++ de la ventana de muestras: compilación/ejecución MSVC correctas
  (calentamiento, orden, contacto, señal plana, saturación y guardas numéricas).
- El usuario completó el paquete base `MeshLink-App1.3.0-FW5.5.0-20261020T032741259Z`
  desde PowerShell normal: contiene APK 1.3.0 y firmware V3/V4.3 compilados.
  Esto no valida las mediciones físicas del sensor.
- Corrección FIFO / diagnóstico r2: pruebas C++ del controlador con bus simulado,
  incluyendo pausa, vaciado verificado, reanudación y recuperación limitada.
  Se verifica también que
  V3/V4.2/V4-R8 sigan sin habilitar el sensor y que la app oculte lecturas
  con los nuevos estados de error. Consultar la guía del diagnóstico para
  el resultado de la compilación ESP32, separado del paquete base.

Las pruebas unitarias no sustituyen compilar y probar el hardware. El registro
físico de r2 mostró 1170 muestras, estados reading, cero desbordamientos FIFO
y recuperación de una lectura I²C incompleta. Esto no valida exactitud clínica.
La app 1.4 y el firmware 5.6/r3 requieren nueva compilación y prueba física.
